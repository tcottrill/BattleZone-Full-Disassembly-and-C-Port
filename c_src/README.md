# c_src — the Battlezone C port

The whole Battlezone program ROM (Revision 1, MAME `bzonea`) translated to C11,
one routine at a time, one file per Atari module. There is no 6502 at runtime:
the C *is* the program. It builds real AVG words into vector RAM, drives the
real Mathbox microcode, writes the real POKEY registers and the `$1840` sound
latch, and **charges the ROM's own cycle count for every instruction path it
runs**, so that the NMI, POKEY's `RANDOM` and the 3 kHz bit see the same time
the ROM would.

Every name is Atari's (the RAM model `state_defs.h` is generated from the
disassembly's defines file), every routine carries its ROM address and
source-line citations, and every call of every routine has been checked
against the running ROM.

## Native arithmetic

The port is plain C, not a 6502 translated instruction by instruction: game
logic uses coordinates, angles, collision tests, decimal scores and counters,
with no CPU registers, flags, carry chains or stack anywhere in the game code.
Routines return domain types (`trig_sample`, `object_contact`); the lockstep
harness converts them to the ROM's register outputs when it compares. Each
path through a routine charges the ROM's cycle total for that path, so timing
stays exact. The separate emulator and the test reference CPU remain the
verification tools. `TRANSLATING.md` has the rules for changing the code.

`tests\build_native_game_boundaries.bat` builds and runs focused ROM comparisons
for explosion arithmetic, shell collisions and score carry, bonus-life thresholds,
missile movement and spawning, initials entry, every tread-control combination
with firing on and off, and object-collision thresholds. Each case checks RAM, vector RAM, hardware I/O,
the routine's checked outputs and exact cycle totals.

## Build

Visual Studio 2022 (x64), no external SDK. From a Windows prompt:

```bat
build_win.bat        rem bz_win.exe
build_all.bat        rem tests\refrun.exe, tests\lockstep.exe, tests\bz_smoke.exe
build_avg.bat        rem tests\avgshapes.exe, tests\avgtime.exe
```

The game, the seam and the host compile at `/W4 /std:c11` with no warnings;
the vendored framework files in `platform/windows/` and the POKEY at `/W3`.

## Run

```bat
bz_win.exe            rem attract mode; coin with 5, start with 1
bz_win.exe --test     rem power on with the self-test switch held on
```

Keys: E/D and I/K drive the left and right treads, the arrows drive both as
a single stick, Space or Left Ctrl fires, 5/6 coin, 1/2 start, F2 flips the
self-test switch (switching it on reboots into the self test), F1 steps the
diagnostics, F3 resets the board, F4 is slam, Alt+Enter toggles fullscreen,
Esc quits. A game pad drives the treads with its two sticks' Y axes, or as a
single stick with its d-pad; button 1 fires, Start starts, Back coins.

`bz_win.log` is written beside the exe. Once a second it records the pacing
(passes, NMIs, pictures, lit segments, their bounding box, the frame rate)
and the audio stream's health: a good run reads `0 starved, 0 flushed`,
queue depth 5 to 7.

## Timing: the port counts cycles

The first playable build took no machine time in translated code and
serviced NMIs only while `MAIN` waited for `SYNC`. Every routine passed
lockstep, yet the enemy tank always backed away: `R_EVAD` (`$6553`) backs off
when `S_INTCT & 7` is zero, and with no time passing inside a pass it was
zero on every call — on the board, where NMIs land all through the pass, it
is zero about one time in nine. The same shortcut made two `RANDOM` reads
return the same byte, so the saucer always appeared on the diagonal. Both
depend on *where inside a pass* time has got to, which no per-pass cost model
can give. So the port counts:

- **Every translated routine charges the ROM's cycles.** `CYC(n)` (`hw.h`)
  follows the instruction stream path by path — taken branches, page
  crossings, loop iterations, the `DTAB` push/`RTS` dispatch — with the ROM
  range in its comment. `python tools\cyc.py 6553-6560` gives any range's
  cost from `progrom.c`; `python tools\cyc_audit.py *.c` flags any charge
  whose comment names a range of a different cost.
- **The NMI lands between instructions, as on the 6502.** `hw_cycles()`
  (`app_loop.c`) advances the machine clock and takes each NMI at the first
  charge after it falls due, paced to the wall clock so the audio stream is
  fed one block per NMI. The `SYNC` and `BUFRDY` spins charge the loop's
  real cycles.
- **Time-dependent reads are charged up to their own instruction.**
  `RANDOM` moves only with spent cycles, so a routine that reads it twice
  charges the cycles between the two reads before the second; the same
  holds for the 3 kHz bit in `IN0`. `tests\bz_smoke.exe --prand` is the
  regression check (64 forced saucer entrances: 64 equal pairs before the
  fix, 1 after).
- **`lockstep --cycles-strict`** compares each call's cycle count with the
  ROM's, in all three scenarios: 0 differ.

The result matches the ROM's own spread: `ROBOT` runs 9 to 13 NMIs into a
pass (the ROM, 6 to 18 depending on the scene), `S_INTCT & 7` takes every
value, and the tank turns aside and waits to shoot.

Not counted: the self test (`bzstst.c`) charges a flat cost per I/O access,
which is all its timing loops need, since they pace themselves on the 3 kHz
bit. A whole run still drifts from the ROM's from power-on, because of that
and because the NMI is placed at the resolution of a `CYC()` block rather
than a single instruction; game behaviour does not depend on either.

## Verification

All of it runs without a ROM: the oracle links the same generated
`progrom.c`, `vecrom.c` and `mbprom.c` the port does.

| tool | what it does |
|---|---|
| `tests\refrun.exe` | the oracle: the ROM on the shared `ref6502` interpreter with the board modelled around it (NMI grid, AVG HALT from walking the list, POKEY, Mathbox microcode, 3 kHz bit, watchdog). `--frames N`, `--script FILE`, `--outdir DIR` (frame dumps, default `tests\ref`), `--capture-every K`, `--snap-pc HEX` (snapshot RAM each time the PC hits an address), `--call-cycles FILE`, `--mbtest` (the ROM's own Mathbox table, 30/30) |
| `tests\lockstep.exe` | the call-by-call verifier: at every call of a translated routine, runs the ROM and the C from the same snapshot with the ROM's I/O replayed, and compares RAM, vector RAM, the I/O sequence and, with `--cycles-strict`, the cycle count. NMIs landing inside a call taint it rather than fail it. `--mutation-check NAME` proves a deliberately broken routine is caught; `--list-untranslated` |
| `tests\bz_smoke.exe` | the real `app_loop.c` and every module behind a headless host with a simulated clock: `[passes]`, `--play`, `--idle`, `--test`, `--diag N`, `--prand`, `--log FILE` (the robot's state every pass), `--svg FILE` (the last picture; `python tools\svg2png.py` makes a PNG) |
| `tests\avgshapes.exe`, `tools\avg_gate_v.py` | Gate V: `avg.c` draws every vector-ROM picture as the disassembly's renderer does |
| `tests\avgtime.exe`, `tools\avg_prom_sim.py` | Gate T: `avg.c`'s cycle count per list, against MAME's AVG state machine run on the real state PROM |
| `tests\scenarios\*.txt` | the input scripts: `attract`, `coin_start`, `play_long` |

```bat
tests\lockstep.exe --frames 5000 --cycles-strict
tests\lockstep.exe --script tests\scenarios\coin_start.txt --frames 3000 --cycles-strict
tests\lockstep.exe --script tests\scenarios\play_long.txt --frames 4000 --cycles-strict
```

| scenario | calls compared | failed | tainted by an NMI | cycle counts compared | differ |
|---|---|---|---|---|---|
| attract, 5,000 frames | 3,140,249 | **0** | 87,048 | 3,053,201 | **0** |
| `coin_start`, 3,000 frames | 1,759,516 | **0** | 46,077 | 1,713,221 | **0** |
| `play_long`, 4,000 frames | 2,511,834 | **0** | 68,562 | 2,442,855 | **0** |

The self test is not in lockstep. Its picture is checked against the ROM's:
`bz_smoke --test` and the emulator's (`../emu_src`) draw the identical HATCH,
alphabet, switch and checksum screen, and the ROM checksums are computed from
the ROM data, not assumed. The RAM tests' bad-memory branches (a lock-up, an
error screen) cannot be reached with RAM that is always good, and are not
translated.

The generators need the disassembly's build output (`../disasm`, run
`gen_from_roms.py` first): `tools\gen_state.py` writes `state_defs.h` from
`bzone_defines.asm`, `tools\gen_roms.py` writes `progrom.c`, `vecrom.c` and
`mbprom.c` from the extracted ROM image. Regenerating reproduces the
checked-in files.
