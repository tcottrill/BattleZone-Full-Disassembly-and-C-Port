# Battlezone hardware

This is what the C port's hardware seam has to reproduce: the 6502 bus as
Battlezone's own code sees it. Sources are Atari's original assembly
(`battlezone-main\BZONE.MAC`, `BZSTST.MAC`, `COIN65.MAC`), Atari's release
documentation (`battlezone-main\BZONE.DOC`), and the AAE emulator driver
(`bzone.cpp`), cross-checked against the ROM images shipped in
`roms\bzone.zip` / `roms\bzonea.zip` and the source-derived binary
`battlezone-main\036414.02`. Every fact below is cited to one of those.

## CPU and clock

6502, clocked at 1.512 MHz (`bzone.cpp:693` and the equivalent
`AAE_CPU_ENTRY` lines for every driver variant, e.g. `bzone.cpp:726, 750,
774, 798, 824, 849`). The POKEY chip runs off the same clock
(`bzone.cpp:118, 136`, both carrying a driver comment `/* 1.5 MHz??? */`
suggesting whoever wrote the AAE driver wasn't fully sure it was exact).

`BZONE.MAC`'s own header claims **"INTERRUPTS: NMI (4 US)"** (`BZONE.MAC:21`).
Take that "4 US" with a grain of salt — see below.

## NMI: rate, source, and a header typo

The NMI is not generated by anything the 6502 writes; it's a free-running
board clock. `bzone.cpp:27-33` documents it precisely:

> Board NMI: the 3 kHz clock (12.096 MHz / 4096 = 2953.125 Hz) divided by
> 12 = 246.09375 Hz, exactly 6144 cycles of the 1.512 MHz 6502. The game
> draws one picture per six NMIs (~41 Hz)... (Was TIME_IN_HZ(240), 2.5% slow.)

`#define BZONE_NMI_HZ (12096000.0 / 4096.0 / 12.0)` (`bzone.cpp:33`), fed
into a host timer callback (`bzone_timer = timer_set(TIME_IN_HZ(BZONE_NMI_HZ),
CPU0, bzone_interrupt)`, `bzone.cpp:378, 388`) that fires
`cpu_do_int_imm(CPU0, INT_TYPE_NMI)` — but only when IN0 bit 4 (self-test
toggle) is **set** (`if (readinputport(0) & 0x10)`, `bzone.cpp:83-87`). The
DIP-switch labelling is inverted from what that reads like: `PORT_BITX(0x10,
0x10, ..., Service_Mode, ...)` pairs value `0x10` (bit set) with the label
`Off` and value `0x00` (bit clear) with `On` (`bzone.cpp:408-410`), and
`BZSTST.MAC`'s own power-on check agrees — `LDA HALT; AND I,ST.BIT; BNE 15$`
skips self test (branches past it into the normal game) when the bit is set,
and falls into `RAMTST` (self test) when it's clear (`BZSTST.MAC:81-86`). So
bit 4 **set** means self test is *off* (normal play), and that's exactly when
`bzone_interrupt` delivers NMIs; bit 4 **clear** (self test *on*) is what
suppresses them.

246.09375 Hz is a period of **4.0635 ms**, not 4 us. The code itself agrees
with 4 ms, not 4 us: the NMI handler counts interrupts in `$INTCT` and
increments the main-loop sync flag `SYNC` every 16th NMI, with the comment
*"IF NOT END OF FRAME (64 MS)"* (`BZONE.MAC:1082-1086`). 64 ms / 16 =
4 ms/NMI, matching the emulator's figure almost exactly (4.0635 x 16 =
65.0 ms). **The header's "4 US" is almost certainly a typo for "4 MS"** —
flagging this explicitly rather than propagating the error into the C port's
timing model. Use 246.09375 Hz (~4.06 ms/NMI) as the authoritative rate.

The game redraws its vector picture once every 6 NMIs, ~41 Hz
(`bzone.cpp:804, 830`: *"~41 Hz picture (6 NMIs), like bzone"*), matching
`BZONE.MAC`'s NMI-handler code: `VTIMER` is loaded with 6 each time the
vector generator is kicked off, and counted down once per NMI
(`BZONE.MAC:1212-1228`, `VTIMER: .BLKB 1 ;VG TIMER` at `BZONE.MAC:283`).

## Reset / interrupt vectors

`BZSTST.MAC:648`: `.VCTRS 7FFA,NMI,PWRON,PWRON` — NMI vector = `NMI`
(`BZONE.MAC:1078`, `$558F`), RESET vector = `PWRON` (`BZSTST.MAC:47`,
`$7ACC`), and IRQ vector is also `PWRON` (the 6502 IRQ line is unused;
if it ever fired, the game would just reset). `PWRON` clears zero page and
all of vector RAM, resets POKEY, tests the self-test switch (see below),
and falls into `MAIN` (`BZSTST.MAC:47-119`).

### IN0 (`$0800`, read) bit meanings

`BzoneIN0read` builds this byte in software from several sources
(`bzone.cpp:158-175`); the `PORT_START` input-port table documents each
bit (`bzone.cpp:401-419`):

| Bit | Meaning | Notes |
|---|---|---|
| D0 | Coin 1 | `IPT_COIN1`, `bzone.cpp:405` |
| D1 | Coin 2 | `IPT_COIN2`, `bzone.cpp:406` |
| D2-D3 | Unused | `IPT_UNUSED`, `bzone.cpp:407` |
| D4 | Self-test / service mode toggle | `IPT_DIPSWITCH_NAME`, `IPF_TOGGLE`, mapped to F2 (`bzone.cpp:408`); gates NMI delivery (`bzone.cpp:81-88`) |
| D5 | "Diagnostic Step" service button | `IPT_SERVICE`, mapped to F1 (`bzone.cpp:411`) |
| D6 | `IN0_VG_HALT` | reflects `avgdvg_done()` — set when the vector generator has finished/halted (`bzone.cpp:37, 171-172`) |
| D7 | `IN0_3KHZ` | synthesized 3 kHz square wave, built from the emulator's own cycle counter (`bzone.cpp:36, 168-169`) |

**Discrepancy worth flagging:** the driver marks D2-D3 "unused", but
`BZONE.MAC` reads bit D3 (`$LMBIT=8`, `BZONE.MAC:199`) as the cabinet
**slam-tilt switch** via `COIN65.MAC`'s generic coin handler (`$LAM=800`,
`$LMBIT=8`, `BZONE.MAC:198-199`; `COIN65.MAC:120-121, 196, 349`). The AAE
driver does not appear to wire a slam switch input at all — slam-tilt is
effectively unemulated in this driver (always reads inactive). `BZSTST.MAC`
also reads D4 (`ST.BIT=10`, `BZONE.MAC:367`) as the self-test switch when
deciding whether to run self-test or jump straight into the game
(`BZSTST.MAC:81-86`), consistent with the driver's D4 assignment.

The self-test ROM ALSO treats D7 (the 3 kHz clock) as a real hardware
timing reference, not just a status bit: it busy-waits on transitions of
that bit to build its own delays (`BZSTST.MAC:213-214`: *"BIT 7 (SIGN
FLAG) OF HALT = 3000 HZ SQUARE WAVE"*). A C port that skips modelling this
edge will make self-test timing loops spin forever or run at the wrong
speed.

### Option switches ($0A00 = DSW0, $0C00 = DSW1)

Decoded from `bzone.cpp:420-461` (`PORT_START("DSW0")`,
`PORT_START("DSW1")`), cross-checked against how `BZONE.MAC` actually
uses each field.

**DSW0 (`$0A00`, `OPTION`):**

| Bits | Field | Values | Game usage |
|---|---|---|---|
| D0-D1 | Lives | 00=2, 01=3 (default), 10=4, 11=5 | `LIVES = (OPTION&3)+2` in `NMI`, on the coin-start/game-begin transition (reached only when the start button is pressed with credits available, `BZONE.MAC:1170-1176`), not on every NMI (`BZONE.MAC:1202-1205`) |
| D2-D3 | Missile-tank threshold | 00=5000, 01=10000 (default), 10=20000, 11=30000 | indexes `MISLVL` table, `(OPTION>>2)&3`, e.g. `BZONE.MAC:3249-3254`, `3720-3725` |
| D4-D5 | Bonus tank score | 00=none, 01=15k&100k (default), 10=20k&100k, 11=50k&100k | indexes `BONTBL`, `(OPTION>>4)&3`, `BZONE.MAC:2542-2549` |
| D6-D7 | Language | 00=English, 01=German, 10=French, 11=Spanish | selects message table via `LNGTBL`, `BZONE.MAC:4097-4103` |

(`bzone.cpp:421-440`)

**DSW1 (`$0C00`, `OPTON2`):** consumed as the coin mode byte `$CMODE`
every NMI (`LDA OPTON2 ;C SET COIN MODE / STA $CMODE`, `BZONE.MAC:1092-1093`),
then decoded generically by `COIN65.MAC`'s macros (`GCM`, `GHM`, `GDM`,
`GBAM`, `COIN65.MAC:73-105`):

| Bits | Field | Values |
|---|---|---|
| D0-D1 | Coinage | 00=Free Play, 01=1 coin/2 plays, 10=1 coin/1 play (default), 11=2 coins/1 play |
| D2-D3 | Coin B multiplier | 00=x1 (default), 01=x4, 10=x5, 11=x6 |
| D4 | Coin A multiplier | 0=x1 (default), 1=x2 |
| D5-D7 | Bonus coins | 000=none (default), 001=3cr/2coins, 010=5cr/4coins, 011=6cr/4coins, 100=6cr/5coins |

(`bzone.cpp:443-461`; generic field layout documented independently in
`COIN65.MAC:54-58` and `169-171`, matching bit-for-bit.)

### Coin/slam handling and electro-mechanical coin counters

`BZONE.MAC` links Atari's generic `COIN65.MAC` coin routine as module
`MOOLAH` (the include directive at `BZONE.MAC:1236` says `.INCLUDE TC65`;
the shipped source is `COIN65.MAC` — the assembled symbol table
(`disasm\build\symbols.json`) records `MOOLAH` under file `TC65.MAC`, so
either the source disk had a copy renamed `TC65.MAC` or the build tooling
substitutes it; flagging as unresolved rather than guessing). `MOOLAH`
runs once per NMI (`JSR MOOLAH`, `BZONE.MAC:1094`) and is configured for
3 coin mechs / 3 electro-mechanical counters (`EMCTRS=3`, `BZONE.MAC:193`;
`MECHS=3`, `BZONE.MAC:196`).

The game maintains **software** pulse timers for the electro-mechanical
coin counters (`$CCTIM`, `COIN65.MAC:207-210, 494-533`) — a nonzero/
negative `$CCTIM(x)` byte means "pulse this coin meter's solenoid on".
**No corresponding hardware output/latch address was found in `bzone.cpp`**
("No coin-counter output write handler... found in `bzone.cpp`" — the
driver simply doesn't emulate the physical coin-meter solenoids, which
makes sense since they have no visible effect on gameplay). A C port
following this driver's lead can drop `$CCTIM` on the floor (it never
becomes visible I/O); a port aiming for the real board would need the
counter output address from a schematic, which isn't in any source file
read for this task.

### Watchdog

`WTCHDG` ($1400) — game writes `CLD; STA WTCHDG` every NMI
(`BZONE.MAC:1090-1091`), driver maps it to `watchdog_reset_w`
(`bzone.cpp:335`). Standard Atari watchdog: if the write stops happening
(CPU hung), the emulator/hardware resets the board.

### Vector generator control ($1200/$1600, status via IN0 D6)

- `GOADD` ($1200, write) — `avgdvg_go_w`: start the AVG executing the
  vector list starting wherever `VGLIST` currently points inside
  `VECRAM`. Triggered once per 6 NMIs from the NMI handler
  (`BZONE.MAC:1226`, `STA GOADD`).
- `VSTOP` ($1600, write) — `avgdvg_reset_w`: halt/reset the AVG. Written
  by the self-test's power-on RAM-clear pass (`BZSTST.MAC:80`) and by the
  NMI handler when the picture buffer isn't ready yet (`BZONE.MAC:1214`,
  `STA VSTOP`).
- Status is read back through **IN0 bit 6**, not a separate register —
  `avgdvg_done()` (`bzone.cpp:171-172`). `BZONE.MAC`'s own equate for this
  same bus address, `HALT=800`, plus its comment `;D0=1 FOR HALTED`
  (`BZONE.MAC:331`) refers to the game's original (pre-AAE-driver)
  documentation of the same signal — note the bit position note in the
  equate comment (D0) doesn't match the driver's D6; only one of the two
  can be the hardware truth, and this wasn't resolved from source alone —
  flagging it rather than picking one.
- AVG variant: Battlezone (and, sharing its board family, Red Baron) use
  the **`avg_start_bzone()`** clipping/timing variant specifically
  (`bzone.cpp:377, 387`, with an explicit comment on the Red Baron call:
  *"MAME 0.111: Red Baron uses the bzone AVG variant"*). This is the
  monochrome AVG with Battlezone's clip window (see the Mathbox `CLIP`
  command in `MATHBOX_NOTES.md`) — video mode is
  `VIDEO_TYPE_VECTOR | VECTOR_USES_BW` for every variant, with
  `VECTOR_USES_OVERLAY1` (a colored plastic overlay film, not a real
  color vector display) added for the upright cabinets and omitted for
  cocktail/Bradley Trainer (`bzone.cpp:707` vs `756` vs `855`).

### Discrete sound / lamp latch ($1840, write) — `SOUND`

`BzoneSounds` (`bzone.cpp:219-267`). The game writes a fresh byte to this
port every NMI, built up in the zero-page shadow `SNDWRD` plus a few
locally-OR'd bits (`BZONE.MAC:1138-1211`).

| Bit | Meaning | Driver evidence | Game-side evidence |
|---|---|---|---|
| D0 (`0x01`) | Explosion enable | "Enable explosion output" comment, triggers sample 7 (`bzone.cpp:241-246`) | `EXPLOD=1` equate (`BZONE.MAC:370`); set/cleared per-NMI from `EXPCNT` (`BZONE.MAC:1123-1130`) |
| D1 (`0x02`) | Explosion size select | sub-selects sample index 4 vs 5 under D0 (`bzone.cpp:242-246`) | `LOX=2` / `HIX=0FD` (AND-mask clearing D1) bracket the "big vs small explosion" bit, e.g. `BZONE.MAC:627-628`, `2371`, `2439`, `3373` |
| D2 (`0x04`) | Shell-fire enable | "Enable shell output", sample 2 (`bzone.cpp:248-253`) | set from `SXPCNT` (shell explosion counter), `BZONE.MAC:1131-1137` |
| D3 (`0x08`) | Shell loud/soft select | sub-selects loud vs soft shell sample under D2 (`bzone.cpp:249-253`) | `LOUDSH=8` / `SOFTSH=0F7` (AND-mask clearing D3), e.g. `BZONE.MAC:2436, 3149-3153` |
| D4 (`0x10`) | Engine "fast" select | combines with D7 for rumble speed (`bzone.cpp:255-266`) | `HIDLE=10` / `LIDLE=0` — tank moving vs idle, `BZONE.MAC:2683-2690` |
| D5 (`0x20`) | Master sound enable | gates POKEY output (`bzone_pokey_w` only forwards when `soundEnable`, `bzone.cpp:152-156`) and kick-starts the idle engine sample (`bzone.cpp:227-232`) | set as part of `ORA I,0A0` in-game (`BZONE.MAC:1142`) or alone as `ORA I,20` ("sound the alarm" comment) when not in a game, e.g. slam-tilt (`BZONE.MAC:1149`) |
| D6 (`0x40`) | LED / start-button lamp | `set_led_status(0, ~data & 0x40)` — inverted (`bzone.cpp:224`) | game comment calls this bit "LICONS" when clearing it, e.g. `;C TURN OFF LICONS` (`BZONE.MAC:1184, 1210`) — meaning of "LICONS" not established from source, flagged as uncertain |
| D7 (`0x80`) | Engine rumble enable | gates the engine-motor sample; combined with D4 picks slow (`0xA0`, "data is 0xa0") vs fast (`0xB0`, "data is 0xb0") rumble, with a `*1.66` frequency scale for fast (`bzone.cpp:255-266`) | set together with D5 as `ORA I,0A0` for in-game audio (`BZONE.MAC:1142`) |

`BzoneSounds` de-dupes identical consecutive writes with a `lastValue`
latch check (`bzone.cpp:238-239`; the sibling `RedBaronSoundsWrite` has the
same pattern at `bzone.cpp:194-195`, but that function is Red Baron's own
sound write handler, not Battlezone's) — a C port doesn't need to
replicate that (it's a sample-restart optimization, not board behavior),
but should know repeated identical writes are harmless either way.

### POKEY ($1820-$182F)

One POKEY chip, base `$1820`, clocked at 1.512 MHz
(`bzone_pokey_interface`, `bzone.cpp:115-131`). Register equates from the
game: `SKCTL=POKEY+0F` ($182F, serial/keyboard control — re-initialized
to `7` on coin-start and at power-on, `BZONE.MAC:1198-1199`,
`BZSTST.MAC:56-57`), `PRAND=POKEY+0A` ($182A, random number register —
used throughout as the game's RNG source, e.g. `BZONE.MAC:670-679`,
`3728, 3781-3782`), `POTGO=POKEY+0B` ($182B, start a pot-scan cycle),
`ALLPOT=POKEY+8` ($1828, the combined pot/digital-input word; also
aliased `AUDCTL` on writes — same address, different register depending
on direction — `BZONE.MAC:403`), `CHAN1F..CHAN4V=POKEY+0..+7` (the four
audio-channel frequency/control pairs).

**Controls read through `ALLPOT`, not individual POKEY pot channels.**
The driver's 8 per-channel POT handlers are all null
(`bzone.cpp:120-128`); the only live analog/digital hookup is the
`ALLPOT` read handler itself, `bzone_IN3_r` (`bzone.cpp:95-105,
177-181`), which reads a discrete "IN3" port plus a single-joystick
"FAKE" port translated through `one_joy_trans[32]` and ORs the two
together — i.e. Battlezone's twin tank levers are read as four
discrete momentary switches packed into the low nibble of `ALLPOT`,
not as POKEY analog pots. The game confirms this: it triggers a pot
scan (`STX POTGO`) then reads `ALLPOT`, masks the low nibble
(`EOR I,0F; AND I,0F`), and uses the value (4-9, all-switches-open/
illegal below 4) as an index into a jump table of the nine tread
combinations forward/reverse/pivot-left/pivot-right/stopped
(`MTAB`, `BZONE.MAC:2633-2648`). The fire button is bit 4 of the same
byte read from `ALLPOT` (`PL1FIR=ST.BIT=10`, `BZONE.MAC:366-367`,
tested at `BZONE.MAC:892, 2694`).

### EAROM

**Battlezone has no EAROM on this memory map.** `bzone.cpp`'s
`BzoneRead`/`BzoneWrite` (and `BradleyRead`/`BradleyWrite`) contain no
`Earom*` symbol anywhere; `EaromRead`/`EaromWrite`/`EaromCtrl` are wired
**only** into `RedBaronRead`/`RedBaronWrite` at `$180C`/`$1820-$185F`
(`bzone.cpp:352, 363-364`). Every driver variant (including plain
Battlezone) does register a blanket `AAE_DRIVER_NVRAM(atari_vg_earom_handler)`
(`bzone.cpp:713` etc.), but with no address decode behind it on Battlezone's
own memory map this looks like inherited board-family boilerplate rather
than a real chip. High scores and settings are therefore volatile: they
live in RAM (`HSCTBL`/`INITLS`, `BZONE.MAC:304-306`) and are reset by
`PWRON`'s zero-page clear on every power cycle (`BZSTST.MAC:53-55`,
`103-117`) — there is nothing for a C port to persist here beyond what
the player wants for its own convenience.

## The 15-bit address decode / ROM mirror

The reset/NMI/IRQ vector table lives at `$FFFA-$FFFF` (6502 hardware
requirement) but Battlezone's source places its vector table at
**`$7FFA`** (`BZSTST.MAC:648`, `.VCTRS 7FFA,...`), inside ROM `036409-01`
which is mapped at `$7800-$7FFF` (`BZONE.DOC:14`). This only works if
`$F800-$FFFF` is a mirror of `$7800-$7FFF`. `bzone.cpp`'s ROM loading
confirms it directly: every ROM set ends with `ROM_RELOAD(0xf800, 0x0800)`
(`bzone.cpp:572, 588, 605, 622, 640, 654, 678` — all seven occurrences in
the file) — the same 2 KB image
is loaded twice, once at `$7800` and again at `$F800`. That is consistent
with the board decoding only 15 address lines (A0-A14) for ROM chip
select and simply not looking at A15, so every chip (and, presumably,
every other decoded device) appears twice, 32 KB apart. No schematic was
read to confirm this beyond the vector-placement/`ROM_RELOAD` evidence,
so treat "A15 is unconnected/ignored by the decode PROM" as a
well-supported inference, not a confirmed fact.

## The two `$5000` ROM images

The source in `battlezone-main\` assembles to a program ROM at `$5000`
whose image is checked in as `battlezone-main\036414.02`
(2048 bytes, **CRC32 `efbc3fa0`**, verified directly against the file).
Atari's own release documentation calls this part **`036414-02`**
(`BZONE.DOC:19`) — but MAME/AAE's `bzonea` ROM set ("Revision 1",
`bzone.cpp:717, 577-592`) loads the *same* CRC `efbc3fa0` image under the
filename **`036414-01.e1`** (`roms\bzonea.zip`). So Atari's own numbering
and MAME's numbering disagree by one revision digit for the identical ROM
image — this source tree matches MAME's `bzonea`, not `bzone`.

MAME/AAE's plain `bzone` set ("Revision 2", `bzone.cpp:683, 562-575`) uses
a *different* `036414-02.e1` image, **CRC32 `13de36d5`**
(`roms\bzone.zip`). Diffing the two 2 KB images byte-for-byte (done
directly against `roms\bzone.zip` and `roms\bzonea.zip`) gives exactly
**149 differing bytes**, in two ranges:

- `$5340` (1 byte) — this is `CHKS2`, a page checksum constant embedded
  in the ROM for the self-test checksum routine (`BZONE.MAC:802`,
  `.BYTE 70`). It necessarily changes whenever anything else in the page
  changes, since the self-test recomputes and compares against it.
- `$54A8-$553C` (148 bytes, in two contiguous runs of 93 and 55) — this
  is inside `CKSCOR`/`DISTBL`, the **high-score table display routine**
  (`BZONE.MAC:810-1020`, `.SBTTL HIGH SCORE STUFF` at `BZONE.MAC:804`).

Both the byte ranges and the "high score table display" characterization
match exactly. **This source tree (and thus a 1:1 C port built from it)
reproduces the `bzonea`/Revision-1 image (`efbc3fa0`)**, not the `bzone`/
Revision-2 image (`13de36d5`) that MAME's default `bzone` set ships. A
port that needs to match MAME's default `bzone` ROM set byte-for-byte in
the high-score display would need the Revision-2 variant of that one
routine, which isn't in this source tree.
