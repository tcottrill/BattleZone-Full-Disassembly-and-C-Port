# Battlezone (Atari, 1980) - annotated disassembly

Byte-exact, fully labelled listings of the Battlezone program and vector ROMs, built by
re-assembling Atari's own source and checked against the ROM image twice: by an independent
read-back verifier and by a ca65/ld65 round trip. A third, independent check
(`check_ramrefs.py`) decodes every instruction straight from the ROM image and proves every
RAM-range memory operand it touches lies inside a named cell in `bzone_defines.asm`. The
format follows the
[Tempest](https://github.com/tcottrill/Tempest-Full-Disassembly-and-C-Port) and
[Space Duel](https://github.com/tcottrill/Space-Duel-Full-Disassembly-and-C-Port)
disassembly projects.

[`bzone_shapes.html`](bzone_shapes.html) draws every vector object the listings describe.

## Regenerate and verify

```
cd disasm
python gen_from_roms.py --check                 # ROMs from ../roms, cc65 from the Tempest project
python gen_from_roms.py ../roms/bzonea.zip --check --cc65 C:\path\to\cc65\bin
```

`gen_from_roms.py` finds the ROM chips by part number + CRC32 (a MAME `bzonea.zip` set -
Revision 1, the one this source tree assembles to - or `bzone.zip` - Revision 2, used only
for the alternate-image diff below; loose files also work), writes
`_survey/roms_extracted/bzone_cpu64k.bin` (+ `bzone_alt_cpu64k.bin` when both sets are
present), then runs:

1. `macasm.py` when its outputs are missing/stale (or `--macasm`)
2. `emit_vrom.py`, `verify_vrom.py`, `emit_shapes.py` (vector ROM track)
3. `emit.py` -> `bzone_program_rom.asm`, `emit_defines.py` -> `bzone_defines.asm`
4. `verify.py` - must print `MISMATCHES : 0`
5. `check_ramrefs.py` - must print `check_ramrefs: OK`
6. `emit_alt.py`, if both ROM sets were found - disassembles the 149 bytes where the other
   `$5000` chip revision differs
7. with `--check`: `emit_ca65.py` - must print `ca65 round trip: 12288 bytes, 0 mismatches`

Any failing step prints `!!` and the exit status is 1. The individual scripts can also be run
on their own in that order.

Current result: verify 12288/12288 bytes, 0 mismatches; ca65 round trip 12288 bytes, 0
mismatches; check_ramrefs 1441 RAM-range operands, all covered or individually explained (2 in
the 6502 stack page, 3 the compile-time base of an indexed instruction whose index is
guaranteed never to reach that low); 120 routine headers (75 source descriptions, 18 of them
from the comments on the calls; 45 written for this disassembly); 121 RAM variables named, all
121 (42 needed a `[note]` description where Atari's own comment was silent, or - for a handful
- described where it actually described the *next* cell, see `bzone_defines.asm`'s Zero page
variables/Game RAM banners); the vector ROM track separately verifies 4096/4096 bytes, 0
mismatches (12 pictures, 37 characters, 42 3-D objects); the alternate `$5000` chip's 149
differing bytes re-encode clean against that image too.

## Inputs, none of them distributed here

- A ROM set: `../roms/bzonea.zip` (Revision 1, MAME part `036414-01.e1`/CRC32 `efbc3fa0` - the
  image this source tree assembles to and the one every listing here reproduces) and,
  optionally, `../roms/bzone.zip` (Revision 2, `036414-02.e1`/CRC32 `13de36d5` - used only by
  `emit_alt.py`, for the 149 bytes that differ). `gen_from_roms.py` matches chips by part
  number and CRC32, not filename, so either set can also be a directory of loose files or a
  differently-named zip.
- Atari's source archive, unzipped so the `.MAC` files are at `../battlezone-main/` (`BZMTNS
  BZONE BZSOUN VGUT BZSTST`, the `BZONE.COM` link set, plus `BZONE.DOC` and `BZONE.MAP` for
  cross-checking). Several modules it `.INCLUDE`s are *not* in that archive and are read from
  elsewhere on this machine via `macsrc.py`'s `ALIASES` (`TC65` -> `COIN65`, `COND65` ->
  `HLL65`, matching-name substitutes for files the archive calls by an older name) and
  `ALT_DIRS` (a search path across this machine's other disassembly projects -
  `red-baron-main`, `Gravitar Dissasembly/gravitar-main`,
  `AAE_publish/AAE_working_stuff/space-duel-main`,
  `Tempest Dissasembly/tempest-main/tempest-main`, and a local `reconstructed/` - for `VGMC`,
  `VGAN`, `ASCVG`, `COIN65`, `HLL65`, `MBDIAG`): the ROM comparison is the proof that a module
  borrowed this way is byte-identical to whatever Atari actually linked.
- [cc65](https://cc65.github.io) for `--check`: this project carries no copy of its own and
  defaults to the one the Tempest project keeps, `../../Tempest Dissasembly/cc65-win32/bin`
  (`--cc65 DIR` overrides it, or it is found on PATH).

## Conventions (program listing)

Identical to the Tempest project's, which battlezone-main's tooling was adapted from:

- Syntax as Space Duel/Tempest's listings (Ophis style): `.org`, `.include`, `.alias NAME
  $VALUE`, `.byte`, `.word`, upper-case mnemonics, `$` hex. `[ ]` groups expressions, `~` is
  one's complement, `|` is OR, `<`/`>` low/high byte.
- Every code/data line starts with its address label `Lxxxx:`. Named labels sit on their own
  line above it. A label that falls inside a line is an `.alias` right after that line - unless
  it belongs to a *different* module than the line it shares an address with (the end address
  of one module coinciding with the start of the next), in which case it is a numeric `.alias`
  written just above the module banner instead, so it never gets attributed to the wrong
  module's code.
- Names are Atari's (6 significant characters in MAC65, so a longer spelling is the same
  symbol as its own first 6 characters), with `.` -> `_` and `$` -> `S_` (`$$CRDT` ->
  `S_S_CRDT`). A name defined twice with different values keeps its name for the main
  definition; a second ROM/RAM/hardware label among the others gets an `_ADDR` suffix.
- Operands are the source's own expressions with the source's symbols (`LDA #CDPLAY`, `STA
  QDSTATE`, `LDA CAM+1,Y`, `.word JEXIT-1`). MAC65 evaluates left to right without precedence;
  the listing makes that explicit with `[ ]`. An expression is used only if it yields exactly
  the ROM bytes; otherwise the operand is hex and the source statement is kept as `(src: ...)`
  in the comment. Numbers-only expressions are printed as hex. Branch targets are always
  labels. The `LAH`/`LXL` byte-pair macros (Battlezone's own equivalent of Tempest's `LDAL` /
  `LDAH` / `LXL`) appear as `LDA #<X` / `LDA #>X`.
- Where the ROM uses an absolute address below `$0100` (an assembler would pick zero page) the
  bytes are raw: `.byte $B9, $48, $00 ;LDA LIVES1,Y (forced absolute)`.
- Data keeps the source's statement layout (one line per source statement, at most 8 bytes or
  4 words per line); macro-generated data carries the macro call as its comment.
- Module banners (`; MODULE BZONE ...`) mark each linked source module (`BZMTNS BZONE BZSOUN
  VGUT BZSTST`; `BZMTNS` contributes no bytes to the program-ROM listing - it is entirely
  vector-ROM data, see `bzone_vector_rom.asm`); `;.SBTTL ...` lines carry Atari's section
  titles where no routine header does.
- Comments: upper case = Atari's source comment (verbatim); for macro statements the macro
  call comes first.
- Routine headers (a `;----` block before each routine entry: a code label that is a JSR/JMP
  target, a jump-table entry, starts a module, or follows RTS/RTI/JMP/BRK): `; NAME -
  description`. Description sources, in priority order: (1) Atari source - the `.SBTTL` title
  starting there, the label's own comment, the comment block above the label; else the comment
  on the calls to it, marked `(comment at the call)`; (2) `[note]` written for this
  disassembly from reading the code (`routine_docs.py`). A label reached only by falling
  through gets no header.
- The 6502 only decodes 15 address bits: `$8000-$FFFF` is an exact mirror of `$0000-$7FFF` -
  RAM, hardware registers, vector RAM/ROM and the program ROM alike, not just the ROM as in
  Tempest's simpler top-of-ROM mirror - so the CPU vectors at `$FFFA-$FFFF` are the `.VCTRS`
  words at `$7FFA` (NMI/RESET/IRQ -> `NMI`/`PWRON`/`PWRON`).

## Conventions (defines)

Sections as Tempest/Space Duel: `Memory map` (descriptive names), `Hardware registers` (Atari
I/O equates with bit notes, cross-checked against the AAE emulator's Battlezone driver (`bzone.cpp`, not distributed here)), `Zero page
variables`, `Game RAM`, `Vector RAM`, `Vector ROM`, `Constants` (every equate the source
defines - Battlezone has no separate ALCOMN-style common-equates file the way Tempest does, so
this is genuinely all of them, not just the ones the listing refers to by name). Format
`.alias NAME $VALUE ;comment`; comments are Atari's own where the source has one. Text tagged
`[note]` was written for this disassembly - a hardware bit note, a description for a cell
Atari left uncommented, or (for a handful of cells - `TRDCTR`, `GARBAG`, `LOGOZ` - where
Atari's own comment on the line evidently describes the *next* declared cell instead, a common
pattern in this source) the cell's own real description plus a pointer to where the original
comment belongs. A multi-byte cell says its size, computed from the source's own `.BLKB`
count (or, for the handful of cells the code also reaches through a different cell's name at a
fixed offset - confirmed by `check_ramrefs.py`'s cross-reference report, not guessed - a note
saying so). Bytes no cell's extent covers are written as plain comments, never invented
`.alias` names: the one anonymous `.BLKB 1` after `$CCTIM` in zero page, the 6502 hardware
stack at `$0100-$01FF`, the 17 bytes between `TRAP2` and `HSCTBL`, and the 1166 bytes from
`YDISP` to the hardware registers at `$0800` that this source never addresses at all.
